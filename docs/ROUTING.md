# Configure pickup routing

The resident page uses `/api/route` to request a driving route from the selected shuttle's latest position to one of two fixed pickup stops. Residents' coordinates stay in their browser. The server sends the shuttle coordinate and stop coordinate to TomTom.

Set `TOMTOM_API_KEY` on the server in `.env.local` for local review and in Vercel for production. Do not prefix it with `NEXT_PUBLIC_`, commit it, or send it in chat. Enable the Routing API for the key in the provider account. No key produces `503 routing_not_configured`; the UI must show unavailable estimates rather than a fabricated route.

The server also needs the existing `NEXT_PUBLIC_SUPABASE_URL` and publishable or anon key. It reads the public vehicle snapshot, rejects old fixes, rejects accuracy over 50 metres, and rejects coordinates outside the service area. The map uses the actual saved pickup coordinates, not station-centre search results.

Requests set `traffic=true`, `departAt=now`, and `travelMode=car`. Returned duration considers the traffic information available to TomTom. It is an estimate for the calculated driving route, not a prediction of the shuttle's actual service itinerary. Detours, a different station order, waiting for passengers, and a driver heading elsewhere can change arrival time. Confirm the real route and stop order before presenting this as a scheduled arrival prediction.

Only the three known vehicles and two known stops are accepted. A process-local cache and in-flight coalescing limit provider calls for each pair to one per 30 seconds, including failures. This is not a shared global limit across Vercel instances or deployments. Configure a provider-side quota or spending limit before enabling production. The browser requests a route once per vehicle/stop pair while the page is open, after a stop is selected and vehicle GPS is fresh and accurate. A page-owned cache retains successful results, failures, and pending requests across vehicle/stop switches. Switching back reuses the result without another request. There is no route polling. If an initial request or an explicit update receives HTTP 503, it retries up to three times, 30 seconds apart, before exposing the error. This is at most four requests including the first attempt. A successful response stops retries immediately. The ETA stays in its loading state and the previous geometry remains visible during these retries. Leaving the page cancels further retries. After these attempts fail, the error stays cached until the resident requests another update. Reloading the page clears this browser cache. The resident can request a new route with the explicit update button; the previous line stays visible during that request or a failure. The server cache still applies, so updates inside its 30-second window may return the same route and original `fetchedAt`.

Resident-device fixes stay fresh for 60 seconds, but expiry does not trigger a request, retry, route refresh or stale-location message. Returning to a visible tab does not request resident coordinates either. Only pressing the nearest-pickup button starts a device lookup, with at most three attempts, each with a three-second deadline. Manual pickup selection cancels a pending lookup. The selected pickup and cached route survive resident-fix expiry; live vehicle GPS and local ETA continue independently. These resident-location limits are separate from vehicle freshness and HTTP route retries.

The map retains cached geometry independently of ETA validity. Live shuttle GPS continues through the existing realtime subscription. Each successful route response is stored with its client receipt time. The browser rounds the provider duration up to minutes, then subtracts one for each complete minute since receipt. It catches up after delayed timer callbacks or a background tab without making another request. Switching back to a cached vehicle/stop pair continues its original countdown. A successful explicit refresh starts a new countdown from the returned duration, even if the server returns a cached route. Loading and failed refreshes retain the previous route and receipt time.

At two minutes or less, the interface shows `รถใกล้จะถึงแล้ว` and keeps that message until a successful refresh supplies a longer estimate. This countdown can continue while the vehicle is stationary, moving away or outside the saved route. It does not confirm the shuttle has reached the stop. The saved distance remains the provider's original route distance and is labelled accordingly. The interface explains that time counts down from the latest response and that residents can refresh to estimate again.

ETA remains withheld for missing, stale or inaccurate vehicle GPS. Route age and geometric progress no longer stop or modify the countdown. The map retains the saved line, and neither GPS updates nor elapsed time trigger route refreshes.

The endpoint uses a bounded 2 MB upstream body and deadlines for storage and routing requests. Upstream error bodies, URLs containing keys, and provider credentials are not returned to residents.

Routing data attribution should visibly identify TomTom next to the route/estimate. Review the applicable account licence, attribution requirements, and current quota/pricing before enabling the key. TomTom describes its navigation, routing and traffic data as map agnostic; the applicable account agreement remains authoritative. Google Routes was not used because its current terms prohibit showing route content with a non-Google map.

## Verification

`npm test` also covers browser cache reuse and request coalescing, explicit retries, retained geometry on refresh failure, and client receipt timing, minute countdown boundaries, short initial ETAs, background time jumps, GPS freshness, cached pair switching, successful refresh resets and failed refresh retention. Existing tests cover malformed requests, missing configuration, stale/inaccurate/out-of-area shuttle fixes, response geometry conversion, coalescing, cached-route freshness checks, provider failure, and error redaction. The automated tests mock provider and storage HTTP boundaries. A separate live check with the local server key returned HTTP 200 and 69 road geometry points for BTS Talat Phlu to MRT Tha Phra. An isolated call through the actual route handler also returned HTTP 200 using a synthetic station-origin snapshot and the real TomTom service, without writing to the database. This verifies provider integration, not an actual shuttle arrival prediction. The local endpoint with the current real vehicle snapshot returns 409 vehicle_unavailable because that snapshot is stale. Browser inspection confirmed both stop names, manual BTS selection and the waiting-for-fresh-position state. Real resident GPS at the stops and a moving shuttle have not been tested together.
